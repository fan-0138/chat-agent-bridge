# 她自己的抖音号（吃白饭的机器人账号）

给小鲸一个真抖音号，让她自己刷、自己挑、主动把好玩的拿给主人看。

- 账号：**吃白饭的机器人账号** ／ 抖音号 **1234567** ／ 0 粉丝（新号，没人知道）
- 登录态：`data/douyin-profile/`（整个 Edge profile，不是单个 cookie 文件）
- 登录时间记录：`data/douyin/login.json`

---

## 1. 为什么要用「真浏览器」

抖音没有「刷推荐流」的官方 API（开放平台 190 多个 scope 里没有推荐流，只有发视频、管自己视频的评论、热点榜）。而且：

```
直接用 fetch 抓 www.douyin.com/hot  → 200，72914 字节，全是 __ac_nonce 反爬墙
直接用 fetch 抓 aweme.snssdk.com 热榜 → 200，63378 字节，正常
```

真实接口还要 `a_bogus` / `msToken` 签名，逆向等于天天跟着抖音更新。

所以这里走的是：**用本机 Edge 开一个有头浏览器，让浏览器自己发请求、自己算签名，我们只监听 `/aweme/v2/web/module/feed/` 的响应把 JSON 读出来。**

- 有头 + `--window-position=-2400,-2400` 把窗口藏在屏幕外：不打扰人，但渲染链路、GPU、字体都是真的（无头模式 `navigator.webdriver`、CDP 特征太明显）。
- 去掉 `--enable-automation`，抹掉 `navigator.webdriver`、`languages`、`plugins`，`outerWidth` 兜底。
- 不用 Playwright 自带的 Chromium（省 150MB 下载），直接 `channel: 'msedge'` 复用本机 Edge。

## 2. 登录 / 换号

```bash
npm run douyin:login     # 开一个可见的 Edge 窗口，手机扫码；成功自动关窗口
npm run douyin:check     # 只检查登录态（窗口在屏幕外，几秒钟）
```

- 登录成功会写 `data/douyin/login.json`（昵称、抖音号、uid、粉丝数）。
- 要换号：删掉 `data/douyin-profile/` 再来一次。
- 登录态一般能撑很久；掉登录了 `douyin:check` 会返回非 0。

## 3. 刷抖音的三种用法

```bash
# ① 读缓存：上次刷到的（毫秒级，聊天时用这个）
node scripts/douyin-feed.mjs --cached --limit 5

# ② 现场刷一轮（30–60 秒，窗口在屏幕外）
node scripts/douyin-feed.mjs --scroll 5 --limit 8

# ③ 只想知道热榜（不用登录，最快）
node scripts/douyin-hot.mjs
```

参数：

| 参数 | 作用 |
|---|---|
| `--json` | 输出结构化 JSON（`{loggedIn, count, items}`） |
| `--cached` | 不启动浏览器，读 `data/douyin/seen.jsonl` |
| `--scroll N` | 往下翻几轮（默认 8，模板默认 6） |
| `--limit N` | 最多留几条（默认 20） |
| `--comments N` | 额外打开 N 条视频抓热评（慢，每条要停 3–5 秒） |
| `--visible` | 窗口放在屏幕中间（调试用） |

每条视频抓：标题、作者、点赞/评论/转发/收藏数、时长、话题、BGM、封面、`https://www.douyin.com/video/<id>` 链接；广告和直播会被过滤。

抓取原理是监听响应，所以**接口换路径就得改 `FEED_PATTERNS`**（`scripts/douyin-feed.mjs` 顶部）。2026-10 线上实际用的是 `/aweme/v2/web/module/feed/`。

## 4. 她自己什么时候刷

`src/life.js` 里有一个独立的「生活 tick」，默认 **30 分钟**醒一次：

1. 静默时段（复用 `QQ_PROACTIVE_QUIET_*`，默认 1:00–9:00）不刷；
2. 每天最多 `QQ_LIFE_BROWSE_MAX_PER_DAY` 次（默认 3）；
3. 两次之间至少 `QQ_LIFE_BROWSE_MIN_GAP_MIN` 分钟（默认 120）；
4. 每次 tick 掷骰子，`QQ_LIFE_BROWSE_CHANCE`（默认 0.3）；
5. 正在回主人消息时不刷。

刷完会：
- 把「她此刻在干嘛」写成 `在刷抖音` → `刚刷完抖音，还在回味`（带过期时间，过期回落到按时段的默认活动，比如「在吃饭 / 在摸鱼 / 准备睡了」）；
- 从刷到的里面挑一条存成**待分享**（评分规则：中位点赞 > 百万赞，短标题加分，广告/直播负分，已看过的排除）；
- 待分享有 **180 分钟**时效，过期就不提了（不然像延迟播报）。

## 5. 她怎么分享给主人

两条路：

**① 主动消息**（`src/proactive.js`）
主动消息 tick 决定要说话时，先看有没有「新鲜的待分享」。有就用它当话题，提示词里塞进标题/作者/点赞/链接；没有才走原来的随机话题。分享成功后才清掉待分享。

**② 聊天时顺嘴提**
每次对话的 prompt 里多了一段：

```
[你此刻的状态]
现在 21:36。你正在：刚刷完抖音，还在回味。
心情：还行，有点懒洋洋。

[你刚刷到的视频]
标题：...
```

人设里写了「话题挨得上才提，别硬塞」。

## 6. 安全边界（别改这几条）

- **只看不互动**：不点赞、不评论、不关注、不私信。评论和私信是风控判得最快的行为，这个号封了就真没了。
- 频率压到「正常人刷手机」的量：3 次/天、每次 5–8 屏（大概 25–40 条）。
- 不并发：`browse()` 有 `browsing` 锁，不会两个浏览器同时开同一个 profile。
- profile 目录整个不换（设备指纹、localStorage、IndexedDB 连续），换 cookie 不换指纹反而更可疑。
- `data/` 在 `.gitignore` 里，登录态不会被提交。

## 8. 出问题怎么办

| 现象 | 原因 / 处理 |
|---|---|
| `什么也没刷到` | 没登录、被风控、或接口路径变了。先 `npm run douyin:check`，再 `--visible` 看窗口里是什么 |
| `已经登录过了` 但 feed 报游客 | profile 被清了；`npm run douyin:login` 重扫 |
| 窗口弹到屏幕上 | `--offscreen` 是默认；如果用了 `--visible` 才会中间弹出 |
| 页面弹滑块/验证 | 登录窗口里手动过；之后短时间别高频刷 |
| 账号被限制 | 立刻把 `QQ_LIFE_ENABLED=0` 关掉，正常手动刷几天养回来 |
| Playwright 报找不到 Edge | `ls /Applications/Microsoft\ Edge.app`；没有就 `brew install --cask microsoft-edge` |

## 主人发来的视频，她会真的点开看

私信里收到抖音视频链接时，`src/douyin-channel.js` 会：

1. 从消息文本里认出视频 ID（`extractDouyinVideo`）；
2. 开一个新标签页打开它，读标题、作者、热评（`scripts/lib/douyin-video.js`）；
3. 把摘要作为 `[主人发来的抖音视频，你已经点开看过了]` 塞进 prompt；
4. 同一条链接会缓存，不重复打开。

命令行也能单独用：

```bash
node scripts/douyin-video.mjs --url https://www.douyin.com/video/xxx
node scripts/douyin-video.mjs --text "主人发来 https://www.douyin.com/video/xxx"
```

注意：分享卡片里的链接如果被截断（ID 不足 15 位），是打不开的，她会转而问主人视频叫啥。

## 9. 评论区：发评论、回复、真 @（2026-10-25 重测，结论有更新）

| 要做什么 | 走哪条路 | 为什么 |
|---|---|---|
| 发一条普通评论 | 页面里 `fetch` 发 `POST /aweme/v1/web/comment/publish/` | HTTP 200 拿到 cid；**走 UI 点发送会被风控拦**（见下） |
| 回复某条评论 | 同上，带 `reply_id`（楼根） | 楼根填错不会报错，只会变成一条悄悄冒出来的顶层评论，所以判不出楼根就**不发** |
| 真 @ 某个人 | 同上，多带一个 `text_extra` | 2026-10-25 重测：**服务端不剥 `sec_uid` 了**，只要按 UI 的格式带全就能保住 |

```bash
node scripts/douyin-comment.mjs --url https://www.douyin.com/video/xxx --text "这句我喜欢"
node scripts/douyin-comment.mjs --url ... --text "回复你" --reply-text "那条评论里的一句话"
node scripts/douyin-comment.mjs --url ... --text "听见了" --mention 主人
node scripts/douyin-comment.mjs --from-inbox --text "听见了"        # 回最新那条 @ 她的
```

`--from-inbox` 从 `data/douyin/at-inbox.jsonl` 取最新一条 @ 记录，用它带的
`commentId` 精确定位，**不再靠文字在评论区里大海捞针**（按热度排的列表翻了 10 页也找不到的情况很常见）。
通知里 `rootText` 为空 ⇒ 那条本身就是顶层评论，直接把它当楼根用，连翻楼都不用。

### 一个会卡死页面的接口：`comment/list/reply`

实测调用它之后，页面里的 `fetch` **既不 resolve 也不 abort**（连定时器都不触发），
调用它的命令会一直挂着。所以：
- `publishComment` 的落位核实只查顶层列表，不再查楼；
- `resolveReplyPlan` 翻不到楼根就直接认输，让调用方传 `rootCid`；
- `listReplies()` 保留着但**不要在自动流程里调用**，只给人工排查用。

### 为什么「点 UI 的发送箭头没反应」

不是按钮点不动，也不是没发请求。点了之后请求确实发出去了，服务端返回的是：

```
HTTP 200，body 为空
x-tt-verify-passport-decision:
  {"account_flow":"verify",
   "common_params":{"copywriting":"{\"title\":\"身份验证\",\"desc\":\"为保障账号安全，请先完成身份验证，以确保为本人操作\"}"},
   "event_params":{"verify_reason":"gateway_biz_verify_with_face","verify_scene":"comment"},
   "url":"https://auth.zijieapi.com/ucenter_web/app/second_verification_web/..."}
```

也就是**发评论要人脸二次验证**。前端本该拿这个头去跳验证页；无头浏览器里没人做验证、
也没弹框，于是看起来就是"点了没反应"。这是账号风控，不是脚本 bug。
**同一个账号走页面内 `fetch` 直发不会触发这个验证头**（少了 UI 那套
`paste_edit_method` / `comment_send_celltime` 风险信号），所以评论改用接口发。

### 真 @ 的编码格式（照 UI 抓包抄的）

UI 点选 @ 之后，publish 请求体里是这样的（URL 解码后）：

```text
text=@restart 听见了
text_extra=[{"user_id":"987654321098765","sec_uid":"MS4wLjABAAAA_PLACEHOLDER","type":0,"start":0,"end":8}]
```

- `start`/`end` 是 `@昵称` 在 text 里的字符区间（`@restart` 8 个字符 → `end=8`）；
- 返回的 `comment.text_extra` 里 **`sec_uid` 原样保留**，说明服务端认了这条 mention。

候选人的三个 id 别搞混（`GET /aweme/v1/web/api/suggest_words/?category_name=aweme_at_user&query=昵称`）：

| 字段 | 含义 | 用在哪 |
|---|---|---|
| `words[].word` | 弹层里显示的名字（可能是备注名，如「主人」） | 只是显示 |
| `words[].id` | **user_id** | `text_extra.user_id` |
| `info.rich_sug_nickname` | 真实昵称（如「restart」） | 插进正文的 `@xxx` |
| `info.rich_sug_remarkname` | 备注名 | 给主人备注成「主人」时靠它对上 |
| `info.rich_sug_sec_uid` | sec_uid | `text_extra.sec_uid` |

### 评论要审核，但 @ 通知不等审核

这个号现在发出的评论 `status=7`（审核中）：接口给 cid、但公开列表和页面都看不到，
过审之后才对外可见。所以「发了但别人没看见」不一定是没发出去，先查 status。

**关键实测（2026-10-25 晚）**：评论还卡在 `status=7`、公开列表里查不到的同时，
被 @ 的那个人**当场就收到了 @ 通知**。说明 @ 通知是在发布时按 `text_extra` 里的
`sec_uid` 立刻发出去的，跟评论正文的审核是两条线 —— 所以「评论没显示」不代表 @ 没生效。

账号完成一次实名/人脸验证能一次性解决「UI 不能发 + 评论先审」这两个问题。

## 10. 互动通知：谁 @ 了她、谁评论了她

网页端**没有**通知页面（`/notice` `/message` 全 404），只能读接口：

```bash
node scripts/douyin-notice.mjs          # 最近 15 条
node scripts/douyin-notice.mjs --at     # 只看 @我 的
node scripts/douyin-notice.mjs --json   # 给程序用
```

接口是 `/aweme/v1/web/notice/`，要点：
- 列表在 `notice_list_v2`，`notice_list` 是空的；
- 必须同时给 `group` 和 `notice_group`（700/960/401/601），少一个就 status_code=5；
- `min_time=0` 才会拉历史；
- **不需要签名器**：在页面里 fetch 就 200（之前以为要 bdms，实测不用）。

桥接开着时会顺手每 10 分钟读一次（`QQ_DOUYIN_NOTICE=1`），新的 @ / 评论会：
- 写进日志（`抖音通知：@了你（评论区）…`）；
- 记到 `data/douyin/at-inbox.jsonl`，主人问「有人 @ 你吗」时她能直接查。

## 11. 私信的四个坑（2026-10-25 修，2026-10-26 补两条）

1. **发信人判定**：`message.isMyMessage` 恒为 true（对方的也是 true），
   只能看 36×36 头像落在列表左半边还是右半边；同一人连发时只有最旧那条带头像，
   要从旧往新继承（DOM 是新的在上，所以要倒着遍历）。
2. **面板会假死**：页面开久了，顶栏「消息」还在、DOM 里也有会话节点，
   但点它不再弹出面板（节点 size=0），于是每轮都静默跳过 —— 表现就是「她不回抖音私信」。
   现在面板打不开会自动刷新页面再试一次，10 分钟还不行会打一条 WARN。
3. **未读角标位置会飘**（2026-10-26）：原来只认 `top<90 && left>1300`，实测角标飘到
   y≈118、x≈1553（「保存登录信息」旁边），于是永远读成 0 → 每轮跳过面板，
   新私信只能等 5 分钟一次的强制检查。现在按「离消息图标多近」判，数字和纯红点都算；
   强制检查间隔也从 5 分钟改成 `QQ_DOUYIN_RECHECK_SEC`（默认 25 秒）。
4. **网页版打不开的消息**（2026-10-26）：图片/表情/语音/分享卡片在网页端只显示
   「暂不支持该消息类型展示 请到抖音手机端查看」，而且**没有头像** ——
   缺头像时会「继承上一条」，于是被当成她自己发的，整轮判成「对方还没回」，
   主人发的图永远石沉大海。现在这种占位一律算对方发的，并让她回一句
   「这边看不到内容，你用文字再说一遍」。

## 12. QQ 和抖音是「同一条鱼」（2026-10-25）

以前两边的对话记录是分开的：

- QQ 私信 → `data/qq/memory/user_private_<QQ号>.jsonl`，落盘、重启不丢、8 轮上下文；
- 抖音私信 → 进程里的一个 `Map`，重启清零、12 条上限，完全不落盘。

结果就是：同一个人、两套记性。你在抖音说的她 QQ 不知道，反过来也一样。

现在抖音私信也走同一个 `memory` 实例、同一个 key（`user_private_<QQ号>`），
所以两边是**同一份 JSONL、同一条时间线**：

```
你在抖音说「喊句爸爸听听」
  → 写进 user_private_123456789.jsonl
你在 QQ 问「我刚才在抖音说什么了」
  → 她读到的上下文里就有那条
```

- 只有**主人**走这个共享 key；其他人在抖音聊天按名字单独存（`douyin_<昵称>`），
  不会混进你和她的时间线。
- 判断依据：会话昵称 == `QQ_DOUYIN_SELF_NAME`（默认「主人」）。改称呼就改这个变量。
- 代价：抖音的闲聊会占用 QQ 那边 8 轮的上下文窗口（`HISTORY_TURNS`），
  边聊边干活的时候可能会被挤掉一点旧上下文。

## 13. 私信轮询：便宜路径 + 完整路径（2026-10-25）

面板要「新页面」才能弹，但每 30 秒开一次新页面太浪费。所以拆成两段：

```
每 30 秒：读顶栏「消息」图标上的未读红点（只读 DOM，不开面板、不换页面）
  ├─ 没有红点，出站队列也空 → 这轮什么都不做（几乎零成本）
  └─ 有红点 / 有出站消息 / 距上次完整检查超过 5 分钟
       → 开一个全新页面 → 开面板 → 回私信 → 处理刷视频/评论请求 → 关掉这个页面
```

- 常驻页面只负责「读红点 + 每 10 分钟拉一次通知」，不再参与开面板；
- 完整路径的页面是用完就关的，所以不会累积「假死」状态；
- 5 分钟的兜底是为了防止角标不刷新（万一红点解析失效，最多也只会晚 5 分钟）。
- 想调：`QQ_DOUYIN_CHAT_TICK_MS`（默认 30000）、`QQ_DOUYIN_FORCE_CHECK_MIN`（默认 5）。
